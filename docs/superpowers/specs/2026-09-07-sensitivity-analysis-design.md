# Sensitivity Analysis — Design

**Date:** 2026-09-07
**Status:** Approved

## Purpose

The methodology decisions in `pipeline/` (financial lag rule, target
threshold, feature scope, missing-data handling, quarterly horizon) are the
project's own working assumptions from `documentation .pdf`, not yet
confirmed by the thesis supervisor (see the WhatsApp thread transcribed
earlier in this conversation, and `thesis_results/RESULTS.md` §7). Rather
than wait idle for his answers, run a one-factor-at-a-time sensitivity sweep:
vary each open assumption independently while holding everything else at the
current pipeline's defaults, and show whether "no model beats the
majority-class baseline" holds across all reasonable variants or breaks for
some specific choice. This is itself a legitimate, reportable piece of
thesis content (a robustness check), and it tells the supervisor conversation
what actually matters vs. what's cosmetic.

## Scope: one-factor-at-a-time, not a full cross-product

A full cross-product of 5 dimensions would be hundreds of runs and
uninterpretable. Instead: 1 base run (= current `pipeline/` defaults,
literally re-deriving the same numbers already in `pipeline/outputs/`) plus
one variant run per alternative value of each dimension, holding all other
dimensions at base. 12 runs total:

| Dimension | Base (current pipeline) | Variants |
|---|---|---|
| Financial lag | quarterly=60d, annual=120d | 30/60d, 45/90d, 90/180d, 120/240d (annual always 2× quarterly, matching the base ratio) |
| Missing-data handling | train-median impute all partial-missing columns | drop rows with any missing active feature; drop rows with >50% of active features missing (median-impute the rest) |
| Up/down threshold | target=1 if return>0 | dead-zone: target=1 if return≥+1%, target=0 if return≤−1%, drop rows with \|return\|<1% |
| Feature scope | all 18 active features | market-only (11 minus dropped); fundamental-only (7 active fundamentals) |
| Horizon/frequency | quarterly panel | monthly panel; weekly panel |

## Why the horizon variant is cheap, not a rewrite

Confirmed by reading the code: `pipeline/lib/features.py`'s market-feature
windows are day-based (`pd.Timedelta(days=91)` etc.), not period-count
based, and `pipeline/lib/target.py`'s `last_trading_day_price`/
`compute_binary_target` operate on arbitrary timestamps, not
quarter-specific ones. The only thing that actually encodes "quarterly" is
`pipeline/_03_build_panel.py`'s `pd.date_range(freq="QE")`. Changing that one
frequency string (to `"ME"` for monthly, `"W-FRI"` for weekly) and reusing
every other function unchanged is sufficient to produce a monthly or weekly
panel. Financial-statement rows still update quarterly/annually regardless
of panel frequency — most monthly/weekly observations within one financial
quarter will reuse the same latest-available financial row via the existing
`is_available`/`latest_available_financial_row` logic. That's expected
behavior (the lag rule doesn't change), not a bug.

## One small additive change to already-frozen pipeline code

`pipeline/lib/lag.py`'s `is_available()` reads `FINANCIAL_LAG_DAYS` (a
module-level dict in `companies.py`) directly — it has no way to use a
different lag value without duplicating the whole function. Add an optional
`lag_days_override: dict[str, int] | None = None` parameter, defaulting to
`None` (falls back to the existing `FINANCIAL_LAG_DAYS` import — **zero
behavior change when omitted**, existing tests untouched). The sensitivity
runner passes its own `{"quarterly": N, "annual": 2*N}` dict when varying
lag; every other consumer (the real `pipeline/_04_features_target.py`)
keeps calling it exactly as before.

No other pipeline file is modified. `pipeline/outputs/` (the "official" run
backing `thesis_results/RESULTS.md` and the main dashboard pages) is never
touched or regenerated by this work.

## Architecture

New top-level `sensitivity/` directory, parallel to `pipeline/`:

```
sensitivity/
  configs.py          # the 12 RunConfig dicts (base + 11 variants)
  lib/
    build_variant.py  # panel + features/target + split + train for ONE config,
                       # parameterized versions of the pipeline stage functions,
                       # reusing pipeline.lib.{companies,prices,lag,target,features}
  run_all.py           # loops all 12 configs, writes summary.json
  outputs/
    <run_id>/
      dataset.csv
      metrics.json
    summary.json       # aggregated: per-run dimension/value/row-count/best-model/baseline/beat_baseline
```

`sensitivity/lib/build_variant.py` reads each company's already-cleaned
`pipeline/outputs/stock_clean/<company>.csv` and `pipeline/outputs/
raw_financial.parquet` (both already built by the frozen pipeline — no
re-parsing of raw CSVs needed), so each variant run only re-does panel
construction, feature/target computation, and model training — the
expensive raw-loading and stock-cleaning stages run once and are shared.

## Frontend

New dashboard page `/sensitivity/`:
- One row per run: dimension varied, value, dataset row count, best model +
  its test accuracy, majority-class baseline for that run, and whether any
  model beat it (badge: green "no" per the thesis's expectation being
  confirmed, red "YES — a model beat baseline" if that ever happens,
  flagged prominently since it would be a significant finding).
- A grouped bar chart: best-model-accuracy vs. baseline, one pair of bars
  per run, so a visual scan shows whether any variant stands out.
- Each run's dimension/value shown as a plain-language description (e.g.
  "Financial lag: 30 days (base: 60 days)"), not just a config key.

## Testing

`sensitivity/lib/build_variant.py`'s config-driven logic (especially the new
missing-data-handling and threshold variants, which are genuinely new code
not already covered by `pipeline/`'s existing tests) gets its own unit
tests under `tests/sensitivity/`. The monthly/weekly panel-frequency change
is verified by an integration-style check (run it, confirm row counts scale
up roughly as expected — ~3x for monthly, ~13x for weekly, relative to the
quarterly base) rather than a narrow unit test, since it's mostly a
frequency-string change flowing through already-tested functions.

## Out of scope

- Full cross-product / grid search across all dimensions simultaneously.
- Changing `pipeline/outputs/` or any file the main dashboard/report pages
  currently read from.
- Automatically picking a "winning" configuration — this is a robustness
  report, not a hyperparameter search; the supervisor's actual answers
  still govern which configuration (if any) becomes the frozen final
  methodology.
